> Journal du chantier. La fiche de mémoire `project_chat_item_icons` n'en garde que l'état et les règles.

Goal: show a 25×25 item icon next to `<ITEML>` equipment links in chat.

**TextLayout `^i` ENGINE FULLY MAPPED + RENAMED IN GHIDRA (2026-06-23 session 2).** The `^i[itemid]` handling is in the SHARED TextLayout engine, NOT per-window — NPC `mes` dialog, ChatWindow log, tooltips and UI window 0x2716 all reuse it. Pipeline:
1. Text enters a scrollable text-area via `UITextArea_AppendLayoutLine` (0x009a6c70, ~30 callers incl. the NPC say/mes box) → builds a layout with `TextLayout_ctor` (0x007ff3e0).
2. `TextLayout_ctor` → `TextLayout_preprocess_escapes` (0x00a92930, \r\n\" unescape) → tokenize loop `TextLayout_LexNextToken` (0x008057f0) / `TextLayout_LexWordOrBreak` (0x00805500) → `TextLayout_dispatch` (caller @0x0080181c) → position children.
3. Lexer chain inside LexNextToken (first to advance wins): inline `^RRGGBB` color; `TextLayout_LexNItemIDTag` (0x00804ff0, `<nItemID..>`→item NAME text); `TextLayout_LexEmoticon` (0x008044e0, `^e[..]`→token 0x236); **`TextLayout_LexItemIcon` (0x00804e00, regex `^\^i(\[\d{1,7}\])*` → `TextLayout_PushToken`(this,0x241)`**; `TextLayout_LexBracketTag` (0x00804b30, `<..>`→0x1b5..0x233); `TextLayout_LexFontTag` (0x00804750, `<FONT/B/I/U>`).
4. `TextLayout_dispatch` routes token **0x241 → `TextLayout_EmitItemIconToken` (0x00800f60)**: re-runs capturing regex `^\^i\[(\d{1,7})\]*`, `operator_new(0x94)` ItemIconWnd (vtable `0x010276dc`), `FUN_00a1cb70` sizes 0x19×0x19 (25×25), stores id digit-string at +0x7c, calls vtable+0x98 (init→load), `TextLayout_AddChildToLine` (0x008005c0) appends to current line (wrap via `TextLayout_BreakLine` 0x00803220). Returns advanced penX.
5. ItemIconWnd vtable+0x50 = `ItemIconWnd_LoadBitmap` (0x00803850): atoi(id)→`BuildItemIconGrfPath`→`유저인터페이스\item\<resname>.bmp`→texture mgr→blit. (Other dispatch handlers: 599=text/newline `TextLayout_EmitPlainTextRun` 0x00801180; style tags→`TextLayout_EmitStyledTextRun` 0x00800b70; 0x236→`TextLayout_EmitEmoticonToken` 0x00800600 = 50×50 emoticon, vtable 0x01027604. `TextLayout_GetCaptureString` 0x00800050 = pull regex capture; `TextLayout_PushToken` 0x00803370 = push 0x30-byte token, type at +0x24.) **So the public typed `^i[<decimal>]` works in ANY TextLayout window incl. NPC dialogs — confirmed on screen.**

**The icon machinery is the `^i[id]` TextLayout escape token — fully client-side, no server.**
- `TextLayout_EmitItemIconToken` (FUN_00800f60): regex `^i[(\d{1,7})]`, creates a 25×25 icon UIWindow (vtable `0x010276dc`), stores the numeric ID string at +0x7c.
- Icon-window vtable `0x010276dc` slot **+0x50 = `ItemIconWnd_LoadBitmap`** (FUN_00803850): reads id at +0x7c, sets magenta colorkey `0xffff00ff`, builds path via `BuildItemIconGrfPath` (FUN_00d5a720) → `atoi(id)` → `ResolveItemResNameById` (FUN_006a2bd0 → FUN_006a0d40, item table `DAT_01255138`) → format `유저인터페이스\item\%s.bmp` (fmt @ `DAT_00fe07d4`, CP949) → loads from GRF via texture mgr (FUN_00a90350/FUN_00a9f030/FUN_00a8d4a0). **Same path as inventory icons** → works for any item the client knows.
- `TextLayout_ctor` (0x007ff3e0) and `Lua_ChatAddLine` (0x0064c7e0)/`Lua_ChatAddLineEx` call `TextLayout_preprocess_escapes` (0x00a92930) **unconditionally** → any text through those paths renders `^i`.

**EMPIRICALLY CONFIRMED + REFINED (2026-06-24): `<ITEML>` is FILTERED OUT entirely before TextLayout — nothing renders (not even literal text).** User tested: a TextLayout window fed `<ITEML>…</ITEML>` shows NOTHING for it. Deduction: the TextLayout lexer itself would emit an unrecognized `<…>` as PLAIN TEXT — `TextLayout_LexNextToken` (0x008057f0) runs the sub-lexer chain (NItemID→emoticon→`^i`icon→bracket-tag→font); when none advance, the caller falls back to `TextLayout_LexWordOrBreak` (0x00805500) which consumes it as a literal word run. So if `<ITEML>` reached TextLayout it would show literally; since it shows nothing, an UPSTREAM sanitizer strips `<ITEML>…</ITEML>` (tag + inner content) before `TextLayout_ctor`. **Net: the TextLayout route loses links COMPLETELY (no icon, no name, no text) — worse than "literal". The 3-hook real-chat solution is the only one keeping links; settled empirically.**

**✅ LIVE-TRACED + CORRECTED (2026-06-24, x32dbg). The earlier "upstream strip" guess was WRONG — `<ITEML>` is NOT stripped at all; it is LEXED then DROPPED AT DISPATCH (no switch case).**
- NPC `mes` dialog renders via `UIRichTextCtrl_AddLine` (0x00806fc0), NOT `UITextArea_AppendLayoutLine` (BP on AppendLayoutLine never fired; BP on AddLine fired). Caller = `UIRichTextCtrl_WndProc` (ret 0x00807a33).
- Text arrives at AddLine **INTACT**: live-read arg = `Lien: <ITEML><ITEM>[Red Potion]<INFO>501</INFO></ITEM>\xa0</ITEML>` (this is the `getitemlink(501)` format — NESTED: `<ITEML><ITEM>[name]<INFO>nameid</INFO></ITEM>\xa0</ITEML>`, different from the chat equip-b62 `<ITEML>` payload). So NO upstream sanitizer.
- **The 8 TextLayout bracket tags, NAMES live-read from the std::string globals:** `<URL>`=0x1b5 (0x01202ce8), `<ITEM>`=0x1d0 (0x01202d78), **`<ITEML>`=0x1f5 (0x01202da8)**, `<NAVI>`=0x1b6 (0x01202d18), `<NAVIL>`=0x232 (0x01202e80), `<MSG>`=0x233 (0x01202e08), `<QUEST>`=0x21b (0x01202f10), `<TIPBOX>`=0x205 (0x01202ee0). **So `<ITEML>` IS a recognized tag (token 0x1f5)** — the old note "`<ITEML>` is NOT in the set" was WRONG (couldn't read the strings statically, assumed).
- **`TextLayout_dispatch` (0x0080181c) switch has cases {599=plain, 0x1b5/0x1b6/0x1d0/0x205/0x21b→`TextLayout_EmitStyledTextRun`, 0x233→MSG link (FUN_007fb0b0), 0x236→emoticon, 0x241→`^i` icon}. There is NO case for 0x1f5 (`<ITEML>`) or 0x232 (`<NAVIL>`)** → those tokens are silently dropped (render nothing). That is the real "filter". The base `<ITEM>`/`<NAVI>` tags ARE dispatched (styled run); only the "L" variants are dead.
- **Consequence:** `<ITEML>` can't render in TextLayout because its token has no dispatcher case — but `<ITEM>` (token 0x1d0) DOES dispatch (styled run). So the conclusion "no `<ITEML>` link in TextLayout" still holds, but the MECHANISM is dispatch-drop, not upstream strip / unknown tag.

**✅ `<ITEM>` IS A CLICKABLE LINK IN TextLayout (verified 2026-06-24).** `TextLayout_EmitStyledTextRun` (FUN_00800b70) → `FUN_00802dd0` constructs a child via `FUN_008371d0` (0xf8 bytes), inits it with `FUN_008448b0`, and calls **`UIItemLinkBtn_OnDraw`** on it — i.e. the styled-tag run is rendered as a `UIItemLinkBtn`, the SAME clickable item-link-button class the chat uses. (End-to-end clickability also needs the host rich-text control to route mouse hits to the child — render-as-link-button is confirmed; click-routing is the only untested link.)
- **Why the user's `getitemlink()` test showed NOTHING, fully explained:** `FUN_00803000` (bracket-tag capture) builds the closing tag from the token type, finds it (`</ITEML>`), captures the WHOLE opening→closing span as the token's content, and advances past the close. So `<ITEML><ITEM>…</ITEM>\xa0</ITEML>` → the lexer matches the OUTER `<ITEML>`, swallows the inner `<ITEM>` link into the 0x1f5 token's content, and dispatch DROPS it → everything vanishes. **The inner `<ITEM>` is never independently lexed because of the `<ITEML>` wrapper.** Corollary: feeding `<ITEM>[Red Potion]<INFO>501</INFO></ITEM>` WITHOUT the `<ITEML>` wrapper would render a clickable [Red Potion] link in an NPC dialog. **So native item links DO work in TextLayout — via `<ITEM>`, not `<ITEML>`.
