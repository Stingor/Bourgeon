## Identity
- Window **id 8**. Live instance @ g_UIWindowMgr(0x0131f4e8)+0x1d4 = **0x0131f6bc** (non-null when open). Destroyed via UIWindowMgr close FUN_00a2e770 case 8 -> UIItemWnd_OnClose(inv,0) + FUN_00a447d0.

## Interaction (CONFIRMED LIVE 2026-06-27 via conditional breakpoint — vtable +0x80 is RIGHT-click, not left)
- **KEY FACT**: vtable slot **+0x80 = OnRButtonDown** (RIGHT-click), NOT left-click. (Mislabeled left for the whole first pass; RO right-click is what opens the item-info window — that's the "no modifier" branch.) LIVE inventory window vtable = **0x103d460** (cart vtable = 0x103d538), read from the live objs at [0x131f6bc]/[0x131f7dc]. Inventory overrides +0x80 with **FUN_0094f380**; the storage/other container class overrides it with 0x0094eee0 (slots +0x74..+0x80 identical ..89e0/a23470/880bb0 then diverge = same virtual method). So 0x0094eee0 is the OTHER window's right-click handler (its ALT cmds 0x38 storage / 0x4e cart), NOT inventory's.
- **Inventory RIGHT-click = FUN_0094f380** (vtable+0x80): hit-test via FUN_00939e30. If item hit: NO modifier -> item-info window 0xc; SHIFT -> dispatcher->vfunc[0x18](**0x14e**, item) = chat <ITEML> link; CTRL -> lock/favorite path (msg 0xa35 via FUN_00c14xxx, gated this+0x10c==1); **ALT -> direct TRANSFER**, gated by (DAT_0131f6d8==0 && DAT_0131f6e0==0) then FUN_00c85fe0(disp)==0 (special bound/quest-item warning, normally 0), then: DAT_0131f770!=0 -> cmd 0x37; else FindWindow(0x271b): found -> 0x33 (storage); not found & cart open (DAT_0131f7dc!=0) & flag(disp+0x5ce) -> **0x4c** (to cart). Dispatch = dispatcher *(0x0121333c) vfunc[0x18] = CMode::SendMsg 0x00c86740 (hooked by us, live first byte E9; won't decompile, SEH; see [[reference_processinput_sendmsg_hook]]).
- **CONFIRMED LIVE**: ALT + right-click an inventory item with cart open -> broke CMode::SendMsg with arg1=**0x4c**, arg2=item index (0x3d), return addr **0x0094f535** = the call site inside FUN_0094f380: `0x0094f530 push 0x4C / 0x0094f532 call [eax+0x18] / 0x0094f535 ...`. So FUN_0094f380's ALT branch IS what does the working cart transfer. **Feature is NOT broken** — it's on RIGHT-click only.
- **Why ALT+LEFT does nothing**: left-click is a DIFFERENT vtable slot (drag&drop grab), with no transfer; that's the manual drag the user falls back to. Left-click slot not yet pinned (not needed).
- **DAT_0131f7dc = CART window** (refreshed vfunc[0x94] sel 0x37 weight / 0x17 item-add; FUN_00cc82a0/FUN_00d54cf0; weight=cur/max /10). disp+0x5ce = one-shot flag (checked !=0, cleared after firing). Transfer cmds: 0x4c=inv->cart, 0x33=inv->storage (FindWindow 0x271b open), 0x37=DAT_0131f770 path.
- **x32 conditional-BP gotcha**: setting a bp on a constantly-hit fn then SetBreakpointCondition races — the bp fires before the condition lands and freezes the game. Set/verify condition is active, then `run`; re-affirm condition if it broke on a wrong arg.
- **Inventory_HitTestItemAt** (0x00939a70): (x,y) -> item-info struct (hit index + item resname/id std::strings; caller frees via FUN_004f08f0). Decompile for exact field offsets.
- **UIItemWnd_OnClose** (0x0095ab20): clears each slot's selection byte (+0x7d) + un-toggles the menu-icon (cmd 0x11e/0xc2).

## Dark mode / colorchip (UI color palette) — 2026-06-27
- **REUSABLE RECIPE (dark-moding ANY window via colorchip — user will do more windows later)**: (1) find the element's colour source by REing its DrawContent — either a hardcoded immediate (`PUSH 0xRRGGBB` just before a DrawText 0x00a25a70 / fill 0x00a1d760 / line 0x00a1d460 call), OR an object colour field set in an init fn (like the tab control's +0x90..0xa4), OR a `.bmp` texture (recolor the file). (2) Route code-drawn colours to colorchip: `ChipColor(x,y)` = FUN_007a6df0 **(__stdcall! ends RET 0x14 — declare __stdcall or you corrupt the stack & crash)** -> build 0x00BBGGRR = (b<<16)|(g<<8)|r. Then PatchValue the immediate (ONCE, from an IN-GAME hook — NOT the plugin ctor, colorchip isn't loaded that early), or write the object field each frame. (3) Users then theme via colorchip.bmp (data\ overrides GRF). Working pattern = src/plugins/inventory_tweaks.cc DrawContentHook.

## Slot-count "X / max" red-at-101 — FIXED 2026-06-30 (server/client inventory-base mismatch)
Symptom: the bottom-left item count turned RED at 101/200 instead of only at full. ROOT CAUSE (confirmed live, x32 attached): the native draw FUN_00946da0 computes the readout max = **100 + DAT_01602354** (client hardcodes a 100-slot base) and uses that SAME value as the red threshold (`used >= max` ⇒ red, CMOVGE @ 0x009474b1). DAT_01602354 = the server-sent inventory expansion. The moonlight server sets **INVENTORY_BASE_SIZE = 200** (src/custom/defines_pre.hpp) and sends `expansion = inventory_slots − 200` (= 0 for a default char) → DAT=0 → readout collapses to "X / 100", red at 101. (Live in-game read: DAT_01602354=0, both adds = stock `83 C1 64` = +0x64; the denominator @0x0094754e and the threshold @0x009474a1 share the identical `100+DAT` formula, so they can't be split by patching one.)
- **Two display sites** (both read DAT_01602354 @0x01602354, add 0x64): red threshold @**0x00947499/0x009474a1**, displayed "/max" @**0x00947545/0x0094754e**. The `83 C1 64` is ADD r/m32, imm8 sign-extended → CANNOT just become 0xC8 (would be −56). 0x01602354 (inventory expansion) is DISTINCT from 0x01602324 (overweight % threshold, kOverweightPct).
- **Three writers** all store the raw server expansion: FUN_00d2c150 (guard <0x65), FUN_00d00b00 (guard <0xc9, + refresh), and the LOGIN dispatcher case **0xb18** (HEADER_ZC_EXTEND_BODYITEM_SIZE, guard <0xc9) inside LoginCharMode_RecvDispatch.
- **FIX (inventory_tweaks.cc DrawContentHook)**: bump DAT_01602354 by the base delta (**kInvBaseDelta=100** = server 200 − client 100) JUST around the g_draw_orig call, then restore. Native then computes max = (DAT+100)+100 = DAT+200 = inventory_slots (real capacity) for default AND expanded chars; red only at full. Draw-scoped so the 3 writers + other DAT readers see the unmodified server value. kInvExpansion=0x01602354. Validated live by writing DAT=100 (user confirmed: shows /200, red only at 200). **Ships on next Release build (deploy when game closed; rewrites integrity hash).**
